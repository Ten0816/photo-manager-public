# Photo Manager — 2026-11-09 安全性改善版（第1段階）

このZIPはユーザー提供の `photo-manager-source.zip` を実際に展開し、既存のAPI/画面をできる限り維持する方針で修正した**ソースコード全体**です。Docker設定、ブラウザUIも含みます。データベース実体・写真・動画・`.env`・`node_modules` は含みません。

> **本番への即時上書きは不可。** 先に現在のアプリ・SQLite・写真データをバックアップし、別環境または少量のテスト画像で操作を確認してください。本開発環境では `npm test` (5件) とJavaScript構文検査まで実施しています。Node依存パッケージのインストールと実稼働Dockerでの全APIの結合試験は未実施です。変更版は**未検証の候補版**です。

## この版で変更した主要事項

- 共有アップロード一時名を UUID に変更し、HDD 内 `.incoming/` へ一時保存。アップロードが完全に終わるまで通常の写真一覧に公開しません。`/tmp`（PiのSDカード）への最大10GBアップロード一時書込を回避します。
- 既存ファイルを上書きしない同一ファイルシステム内ハードリンク移動 `moveFileNoOverwrite` を導入。適用対象は一括移動、削除によるゴミ箱移動、復元、名前変更など。コピー/移動先の同名ファイルとの競合で既存データを失わない設計です。**ファイルシステムがハードリンクに非対応の場合、移動は安全に失敗します。** NTFS3・ext4では通常利用できますが、実機で確認してください。
- メディア一括移動で同一移動先のファイル名重複を事前に拒否します。
- `MEDIA_DIR/.photo-manager-storage-id` という**事前作成するマーカーファイル**を読み取れなければ全APIファイル操作・定期スキャン・ゴミ箱期限削除を停止します。スキャンが失敗した回はゴミ箱の期限削除を実行しません。
- フォルダの名前変更時の SQL LIKE `_` `%` ワイルドカード問題を修正し、DB更新エラー時にフォルダ名をロールバックする処理を追加。
- 写真・動画サムネイルを `元ファイル名.拡張子.thumb.jpg` に変更して拡張子違いの衝突を回避。サイズ・更新日時を照合して古いサムネイルは再生成。FFmpeg同時実行を最大2に制限（環境変数 `THUMBNAIL_WORKERS` で1〜4設定可能）。一時ファイルで生成して公開するため、作成中のサムネイルが返りにくい設計。
- メディア移動・リネーム後に旧キャッシュを無効化、フォルダ名変更時はキャッシュディレクトリも移動。旧方式で残ったキャッシュは `npm run thumbnails:prune`（確認）→ `npm run thumbnails:prune -- --apply`（削除）で整理可能。
- スキャンでファイルサイズ・更新日時が変わった写真は EXIF 撮影日時を再取得。シンボリックリンクをスキャン対象から除外。
- ゴミ箱を空にする操作は、**1件ずつファイル削除の成功後にDBから削除**する方式に変更。
- APIページの取得上限を200件へ制限、ZIPダウンロード上限を1000件／合計20GiBに制限し、対象を全件事前検証。
- ログイン試行回数制限（15分につき6回）、ランダムなDB管理セッション、明示的なログアウト失効機能を導入。更新後は**すべての既存ログインセッションが無効**になり、再ログインが必要。
- HTTPS接続でCookieに`Secure`を付けるよう改善。TLS終端が別のリバースプロキシの場合は `.env` に `COOKIE_SECURE=true` を設定します。**HTTPSサーバー自体の構築はしていません。**
- DB整合性をチェックする読み取り専用 `npm run audit`、SQLite Online Backup API を使う `npm run backup:db` を追加。Docker Composeに1日1回のSQLiteバックアップサービスを追加（30日で古い自動バックアップを整理）。**同じSDカード内のバックアップだけではSDカード故障対策にならない**ため、外部媒体にも複製してください。
- Node組み込みテストを追加 (`npm test`)。SSH上で依存ライブラリをインストールしてから実施してください。

## 重要：初回起動前の準備

元のDocker構成では `MEDIA_DIR=/data/Memory` がホスト `/mnt/photo-hdd/Memory` に対応します。

```bash
# 以下は Raspberry Pi のホスト側で実行。
# 本当に /mnt/photo-hdd に外付けHDDがマウントされていることが必須。
mountpoint -q /mnt/photo-hdd || { echo 'HDDがマウントされていません。中止'; exit 1; }
findmnt /mnt/photo-hdd
printf 'photo-manager-storage-v1\n' > /mnt/photo-hdd/Memory/.photo-manager-storage-id
```

マーカーはHDD内に**一度だけ作成するファイル**です。アプリは自動生成しません。これがない状態では、メディア操作APIがHTTP 503を返し、定期スキャン・ゴミ箱クリーンアップが失敗終了します。HDD切断時にマーカーがホスト側へ誤作成されないよう、作成時のマウント確認を省略しないでください。

### 安全な適用の順序

1. 既存の写真・動画を可能なら**別の物理ディスク**へバックアップ。
2. 現行アプリのディレクトリで `docker compose down` を実行し、停止した状態で `data/`（WAL等を含む）を丸ごと別の場所へコピー。ソースと `.env` も別にバックアップ。
3. 新ZIPを**別フォルダへ展開**して元のコードと比較し、既存プロジェクトのソースだけをコピーする。`data/` と `.env` は新ZIPに含まれないため、元のものを維持する。
4. 上記のマーカーを作り、**テスト用の写真・動画で**アップロード、同名アップロード、一括移動、名前変更、削除、復元、動画サムネイルを確認する。
5. `npm ci` → `npm test` でテスト。その後 `docker compose up -d --build` を実行して、`docker compose logs --tail=100` でエラーを確認。
6. `npm run audit` でDBとファイルとの整合性を確認（Dockerの実行ユーザーで実行する場合は `docker compose exec photo-manager node audit-storage.js`）。
7. 本番データを扱う前に、実際に復元できるバックアップがあることを確認する。

既存の `.env` に `SESSION_SECRET`, `AUTH_USERNAME`, `AUTH_PASSWORD_HASH` の設定が必要です。セッション変更でログインし直しになります。

## 旧サムネイルの整理

```bash
# 初回は削除しないドライラン
node prune-thumbnails.js
# 表示内容を確認後のみ実施
node prune-thumbnails.js --apply
```

旧キャッシュは残っても写真実体には影響しません。**不要だと確認できた時のみ**実行してください。自動消去はしません。

## 残る重要課題

- 最優先：ファイル操作の**永続的な操作ジャーナルとクラッシュ時の再開/安全な巻き戻し**。現状でも、処理途中にコンテナ/OSの電源が落ちるとDBとファイル名がずれる可能性は残ります。`npm run audit` で不整合を検出できても、自動修正はしていません。
- 次：自然順ソートの仕様を維持したSQL側のページング、HDDの負荷が低い増分スキャン方式、さまざまなAPI操作の結合テスト。
- HTTPS：インターネットに公開する場合はTLSを設定し、`COOKIE_SECURE=true` にしてください。Tailnet内部アクセスの前提は維持しています。
- サムネイルのインメモリ・キューは単一サーバープロセス内の制御です。複数のAPIコンテナを起動する場合はプロセス間排他が別途必要です。

## 取り扱いに関する注意

元のアップロードZIPには `data/photo-manager.db.before-gps-removal` というSQLiteバックアップが含まれていました。この配布ZIPでは**DBを一切収録していません**。今後GitHubへコミット・共有する際はDBのバックアップやGPSを含む個人データを含めないよう、`.gitignore`/`.dockerignore` のほか、**コミット済みのファイルの有無も確認**してください。`.gitignore` は既に追跡済みのファイルを消す機能ではありません。
